# 一、项目整体与业务：基本必问

## 1. 先整体介绍一下这个权限治理平台。它主要解决什么问题？你负责的模块是什么？

> 追问通常会落到：为什么原来的权限系统需要统一治理？“权限管理、回收、交接、审计”分别解决什么业务问题？你做的事情在整个系统链路中处于什么位置？

> 这个项目从用户进入页面，到最终查询到权限数据，完整链路是怎样的？

这个项目是一个面向公司内部的统一权限治理和合规审计平台。它的核心背景是原来的权限能力比较分散，不同业务系统可能各自维护自己的权限数据和管理入口，所以从公司治理的视角，很难统一回答“一个人现在拥有哪些权限、这些权限从哪里来的、是否应该继续保留、发生人员变动后怎么处理”这些问题。我们这个平台做的事情，就是**把这些分散的权限能力进行统一治理，提供权限管理、查询、回收、交接以及审计等能力，并对权限的整个生命周期进行追踪。** 项目资料里明确描述的目标就是解决权限管理分散的问题，实现权限数据集中管理、查询和生命周期追踪。

原来如果权限散落在各个业务系统里，通常会产生三个问题。第一是“看不清”，一个员工到底有哪些系统权限，需要分别去不同系统查；第二是“管不住”，员工转岗、离职以后，一些旧权限可能没有及时回收，形成残留权限；第三是“审不明白”，出了问题以后，很难快速还原某个权限什么时候申请、什么时候生效、后来有没有发生变更。所以统一权限平台本质上不是单纯做一个权限列表页，而是在解决权限资产统一可见、权限生命周期统一治理以及合规审计的问题。

“权限管理”解决的是权限的日常治理问题，比如查询某个人当前有哪些权限、某个权限对应哪些用户，以及对权限进行申请、变更或者管理。

“权限回收”主要解决的是权限生命周期结束的问题。比如员工离职、转岗，或者某项临时权限已经过期，这些权限如果一直保留下来，就会产生越权或者残留权限风险，所以需要有统一的回收机制。

“权限交接”主要对应组织和人员变动。比如一个负责人离职或者岗位发生变化，他原来负责的一些系统资源、管理权限不能简单删除，而是需要转移给新的负责人，所以平台需要支持权限或者资源责任关系的交接。

“审计”解决的是可追溯性。也就是之后能够回答“谁在什么时候拥有过什么权限、权限发生过什么变化”，方便安全、合规或者内部审计场景进行追踪。

假设用户进入“权限查询”页面，整个链路大概是：

用户 → 主应用 → 权限微应用 → 查询页面 → BFF API → BFF Service → 下游 RPC 服务 → BFF 聚合/裁剪 → 前端 → 表格展示

具体来说，用户首先进入统一平台。主应用负责整体路由、登录态以及微应用加载，根据当前 URL 匹配到权限相关路由以后，把对应的权限子应用挂载起来。微前端架构里主应用本身就承担认证、路由、全局能力和微应用注册加载这些职责。

进入权限查询页面之后，页面会先从 URL 中恢复当前查询状态，比如 keyword、filters、page、pageSize、sortField、sortOrder 等。你们页面状态方案是把 URL query state 作为列表查询条件的单一来源，再由这些状态组装接口请求参数。 Formily Schema 则负责根据当前权限场景生成对应的搜索区域，表格列配置决定最终展示哪些字段。

用户点击查询之后，前端不会直接调用底层 RPC，而是请求我们的 BFF。BFF 位于前端和 RPC 服务之间，本身可以处理登录态、粗粒度鉴权、参数处理以及接口编排。懂车帝 BFF 的内部规范也是把 SSO、权限系统插件、RPC 调用作为基础能力提供的。

进入 BFF 后，请求首先进入 API 层，完成参数解析和校验，然后通过依赖注入拿到对应 Service。你们 BFF 文档里的典型实现就是 API Handler 里通过 useInject(TestService) 获取 Service，再调用 Service 方法，这样 API 层不直接依赖具体 RPC 实现。

Service 再根据当前页面需要去调用一个或者多个下游 RPC。例如一个权限列表最终展示的数据可能来自权限主体信息、权限资源信息或者其他领域能力，BFF 会负责把这些结果组合起来，只留下前端真正需要的数据。你们简历里明确描述的就是“对多个下游 RPC 服务进行接口聚合、数据裁剪等编排与调用”。

最后 BFF 把已经整理好的 View Model 返回前端。前端拿到结果以后，不需要再理解底层几个 RPC 的数据结构，而是直接按照当前表格配置渲染权限列表，同时更新分页等状态。

> 用户进入统一权限平台以后，主应用根据路由加载权限微应用；查询页根据 URL 恢复筛选、分页和排序状态，并由 Formily Schema 生成搜索区域。用户发起查询后请求进入独立部署的 BFF，BFF 完成认证鉴权和参数处理，通过依赖注入调用 Service，Service 再编排多个下游 RPC，把不同权限服务的数据进行聚合和裁剪，最终返回统一的数据模型，前端按照表格配置完成渲染。

# 四、BFF：我认为这是你这个项目里最值得深挖的一块

## 1. 为什么需要 BFF？前端为什么不直接调用后端 RPC/HTTP 服务？

我们引入 BFF 不是因为前端不能调用后端，而是因为权限平台的页面存在明显的多 RPC 聚合、数据裁剪和鉴权需求。如果前端直接依赖这些底层服务，会导致前端承担服务编排、与多个领域接口强耦合，同时暴露内部 RPC 细节。因此我们通过 BFF 向前端提供面向页面的稳定 HTTP API，BFF 内部再通过 RPC 调用各领域服务并完成聚合和裁剪。

## 2. 为什么使用 Formily，而不是自己根据 JSON Schema 写一个动态表单？

权限查询页本身有很多相似页面，基本都是搜索条件加列表，所以我们没有每个页面单独写 JSX，而是把搜索条件抽成 Formily Schema，把列表字段和排序抽成 Table columns 配置。Schema 里主要描述字段 name、类型、x-component、组件 props、校验和联动，公共 Renderer 根据 Schema 生成表单；提交以后再把 values 转成 BFF 查询参数，返回的数据按照 columns 渲染。之所以选择 Formily 而不是自己做 JSON Renderer，是因为简单动态渲染很容易，但一旦加入字段状态、校验、联动、异步数据源、复杂结构，就会逐渐变成自己维护一套表单框架。Formily 已经提供 Schema、Field Model、响应式联动和组件注册机制，我们只需要维护业务配置，成本更低。

# 六、nuqs + URL 状态

## 1. 为什么要把筛选、分页、排序这些状态放进 URL，而不是 Zustand 或 localStorage？

我们不是因为 URL 比 Zustand 或 localStorage 更能“存数据”，而是因为筛选、分页、排序本质上属于页面语义状态，它们决定当前页面展示的内容。放进 URL 后可以天然支持刷新恢复、浏览器前进后退、链接分享和直接进入指定查询状态，而且 URL 可以作为查询条件的单一数据源。Zustand 更适合跨组件共享上下文，localStorage 更适合用户偏好和草稿，它们都不适合作为列表查询状态的唯一真相源。

## 2. 为什么要用 nuqs？直接使用 URLSearchParams 不行吗？

URLSearchParams 当然可以，我们也评估过。简单页面只有一两个 query 参数时，我认为原生 API 就够了。问题是权限查询这种中后台页面通常会同时管理 keyword、filters、page、pageSize、sort 等多个参数，直接用 URLSearchParams，需要业务层自己反复处理 parse、serialize、默认值、类型转换、批量更新以及 push/replace 等 history 细节。nuqs 相当于在 URLSearchParams 之上提供了一层 React state abstraction，把这些通用工程问题收敛掉，让 URL state 的使用方式更接近 useState。所以我们不是为了“能修改 URL”而使用 nuqs，而是为了统一和工程化地管理 URL 状态。

写入 URL：序列化

```
number / boolean / array / object
        ↓
      string
```

读取 URL：反序列化

```
string
  ↓
number / boolean / array / object
```

比如数组也是一样。程序里：

```
const status = ['active', 'expired'];
```

可能序列化成：

```
?status=active,expired
```

读取以后：

```
const status = params.get('status').split(',');
```

又恢复成：

```
['active', 'expired']
```

这就是为什么前面说 nuqs 能减少很多重复代码。你直接用 `URLSearchParams` 时，这些转换经常都要自己写：

```js
const page = Number(params.get('page') ?? 1);
const enabled = params.get('enabled') === 'true';
const tags = params.get('tags')?.split(',') ?? [];
```

而 nuqs 的 parser / serializer 就是在帮你统一处理这些：

```js
const [page, setPage] = useQueryState('page', parseAsInteger.withDefault(1));
```

你代码里拿到的直接是数字: page === 3

设置：setPage(4);

它再帮你序列化成 URL：?page=4

> 序列化就是把程序里的对象、数组、数字等数据转换成方便存储或网络传输的字符串/字节格式；反序列化就是把这些字符串/字节重新恢复成程序能使用的数据结构。在 URL 参数场景里，因为 query 参数本质上是字符串，所以读写数字、布尔值、数组时都需要做序列化和反序列化。

## 3. 如果 URL 里已经是 page=5，用户修改了筛选条件，这时候 page 应该怎么办？

这是一道非常容易问到、而且很体现实际开发的问题。

正确思路一般是：

筛选条件改变 → page 重置为 1。

否则原来：

department=A&page=5

改成：

department=B&page=5

B 可能只有两页，页面就会显示空数据。

# 七、网络 / RPC / 浏览器相关八股

## 1. RPC 和 REST API 有什么区别？为什么内部服务之间使用 RPC，而前端通常通过 HTTP API/BFF？

这是从你 BFF 描述中非常自然的一道八股题。

核心就是：

RPC 更强调“调用远程函数”，适合内部服务间通信，通常有严格 IDL、序列化协议和代码生成；

REST 面向资源，基于 HTTP 语义，对浏览器和开放 API 更友好。
